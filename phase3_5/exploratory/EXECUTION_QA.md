**What happened or was decided:** After the first generation (commit `3c22d50`: 596 rows) the analyst noticed that `src/doom/d_main.c` produced no candidate for `gameversions[]`, an array whose element type is an anonymous struct (`static struct { ... } gameversions[] = {`). Handling: a fixture and a failing test first (`191ca9b` -- whose message wrongly claimed GREEN; the patch step before it had failed and the command chain did not stop -- corrected by `1848074`, which carries the pattern change), then the table regenerated: 618 rows (K1 525, K2 78, K3 0, K4 15); the 22 added rows are listed in the regeneration commit's message; no row removed; `cand_id`s renumbered, which is harmless because no verdict had been written against generation 1 (`3c22d50` stays in history as that generation).

## XQA-05 -- the EN2 test and the EN4 test, stated before the first verdict; one XQA-03 example withdrawn (2026-10-29)
**Step:** X4b   **Clause(s):** sealed 3.2 EN2 and EN4; design 6.2; XQA-03
**What happened or was decided:** Reading the 618 candidates showed that XQA-03's line between EN2 and EN4 was not yet operational for the commonest shapes in this tree (mapping tables, dispatch tables, the dehacked loader's vocabulary tables, lists of supported devices). The two tests used for every row:
EN2 -- the project's own identification of the set (its name, the comment at its definition, or a document naming it) must itself speak of acceptance, recognition, support, validity, compatibility or allowance. A set identified as "valid modes", "supported game versions", "known IWAD filenames" or "the sections the loader recognises" passes; a set identified as a mapping, a dispatch list, defaults, data, resources or presentation fails, even if a lookup in it can miss. The quoted identification is the evidence either way.
EN4 -- design 6.2 as written: a located code path in which external input is matched against the set and a miss leaves that input unaccepted -- by an error, a warning, or a silent skip; all three refuse the input, and what separates refusal from selection is that the input can miss and is then not acted on -- or project text saying so. A set that is only indexed or iterated, or whose miss still accepts the input through a fallback, fails EN4.
Withdrawn in place from XQA-03, marked there: "a table of recognised configuration names whose miss is silently skipped passes EN2 and fails EN4". Under the tests above `m_config.c`'s defaults lists are identified by the project as default configuration values, so they fail EN2 and the EN4 question is not reached; and a silent skip is a refusal, not a selection.
**Effect on the record:** every REJECT at EN2 quotes the identification; every REJECT at EN4 names the missing refusal path. The reading not taken -- EN2 as any named scope -- would move most EN2 rejections to EN4 and change no admission.
